# 角色行动逻辑：合并与去重分析

分析对象：`src/prototype/Creep/action/**` + 其共享层 `src/prototype/Creep/function/**`。
目标：找出「高度相似、可以合并」的行动逻辑，降低臃肿度。

> **状态：第 1 轮已实施**（见文末「已实施」）。下面是分析原文，数据为分析时点。

## 方法

两条量化线索，都可以复核：

1. **逐字重复**：把每行归一化（去注释、字符串/数字占位、压缩空白），统计同一条语句出现在多少个角色文件里。
2. **两两相似度**：两个文件共享的语句数 ÷ 较小文件的语句数。

**这个方法的盲区必须说明**：它只抓「复制粘贴」，抓不到「同一个概念、两套写法」。
后者的典型例子见文末「顺带发现」，需要人读代码才能发现。

数据脚本：归一化语句集 → `Map<语句, Set<文件>>`；未纳入版本库（一次性分析用）。

## 结论按收益排序

### 簇 1 · 绑定伙伴（bind）块 —— 4 个文件逐字复制，收益最高

同一段 32~34 行的代码被完整抄进 4 个文件：

| 文件 | 位置 | 行数 |
|---|---|---|
| `combat/defend-duo.ts` | L4–35 | 32 |
| `remote/deposit/deposit-combat.ts` | L3–36 | 34 |
| `remote/outmine/out-duo.ts` | L3–36 | 34 |
| `remote/power/power-combat.ts` | L3–36 | 34 |

共享内容（逐字相同）：`resolveBoundPartner`（取绑定对象、失效则 `delete creep.memory.bind`）、
`tryBindNearestPartner`（房间 tick 缓存里挑最近的、未被绑定的同伴、双向写 `memory.bind`）、
以及候选过滤 `candidates.filter((c) => !c.memory.bind)`。
相似度佐证：`deposit-combat ↔ power-combat` 共享 62 条（58%）、`deposit-combat ↔ out-duo` 34 条（62%）。

**做法**：抽 `src/prototype/Creep/function/boundPartner.ts`，导出
`resolveBoundPartner / tryBindNearestPartner / releaseBoundPartner`。
4 个角色各删 ~34 行，换来 ~60 行共享模块 → 净省 ~70 行，且「同伴绑定」从此只有一处语义。

### 簇 2 · 战斗通用块：自愈 + 治疗同伴 + 跟随

`let healed = false; creep.heal(creep); healed = true;`
`if (!healed && isNearTo(bind)) heal(bind); else if (inRangeTo(bind,3)) rangedHeal(bind);`
`else if (!isNearTo(bind)) moveTo(bind);`

出现在 **6 个文件**：`combat/defend-duo`（L60–72）、`combat/double-heal`（L11–72）、
`combat/pc-heal`、`remote/deposit/deposit-combat`、`remote/outmine/out-duo`、`remote/power/power-combat`
（`combat/one-ranged`、`remote/outmine/out-combat` 是部分的同形）。

**做法**：簇 1 的模块再加一个 `runHealAndFollow(creep, partner)`，各角色只保留自己的「攻击/拆墙」分支。

### 簇 3 · 三个并行的战斗族：24 个 handler 其实只有 4 种行为

| 族 | 文件 | handler 数 | 行数 |
|---|---|---|---|
| 外矿 | `remote/outmine/out-combat.ts` | 4（out-attack/ranged/defend/invader） | 308 |
| Power | `remote/power/power-combat.ts` | 3（power-attack/heal/ranged） | 322 |
| Deposit | `remote/deposit/deposit-combat.ts` | 3（deposit-attack/heal/ranged） | 218 |
| 防守 | `combat/defend-single.ts` / `defend-duo.ts` | 2 + 2 | 254 / 159 |
| 双人 | `combat/double-attack.ts` / `double-dismantle.ts` / `double-heal.ts` | 3 | 195 / 178 / 84 |
| 其它 | `combat/one-ranged.ts`、`combat/pc-heal.ts`、`combat/aio.ts` | 3 | 77 / 93 / 328 |

这 11 个文件共享的行为只有四类：**近战攻击、远程攻击、治疗、拆建筑**，差别在
「去哪个房 / 打什么目标 / 用哪个 body」。三个族的结构完全相同——
每个文件都是一串 `runXxx(creep)` 再加 `const outAttack = { run: runOutAttack }` 这样的薄包装
（`out-combat.ts` L291–305、`power-combat.ts` L309–319、`deposit-combat.ts` L205–215 三处同形）。

**做法**：一个参数化的 `combatAction({ targetRoomSource, targetFilter, mode })`，
族文件退化成「配置 + 导出」。预期 848 行（三族）→ ~350 行。

**角色层合并要先核对孵化配置**（见「风险」）：三个族的 `RoleDefinition` 体型各不同
（如 `out-attack` [ATTACK 19, MOVE 25, HEAL 6] vs `deposit-attack` [ATTACK 25, MOVE 25]），
而 `out-2attack`/`out-2heal`/`out-defend`/`out-invader` 的 `bodypart: []`，体型来自逐级表。
**已有先例**：`aio` 与 `saio` 共用 executor `aio`；`power-heal` 与 `pc-heal` 体型完全相同
（都是 [MOVE 25, HEAL 25]）却分了两个 executor——这类是最容易合的角色对。

### 簇 4 · `double-attack` ↔ `double-dismantle`：整块战术骨架重复

共享 **64 条**语句（各 ~100 条实质语句），包括整函数：
`FlagActionMove`（L21 ↔ L10）、`AutoFindTarget`（L63 ↔ L37）、
敌对建筑枚举（rampart/wall/extension/tower/spawn/observer/factory/storage/terminal/nuker/powerSpawn）、
`creep.doubleMoveTo(...)` / `doubleFlee()` 调用序列、以及 `runLegacy` 里的 bind 兜底路径
（L155–191 ↔ L131–174）。
两者唯一实质差别是「打 ATTACK」还是「打 WORK」，其余是复制。

**做法**：抽 `combat/doubleTactics.ts`，攻击/拆墙只传 `{ bodyType, action }`。

### 簇 5 · 两个微型升级角色：`aid-upgrade`(55 行) 与 `up-upgrade`(107 行)

共享 14 条实质语句，占小文件的 **64%**——两者都是「取能 → 升级控制器」，
差别只在取能来源（本房 vs 援助目标房）。属于**可以直接合成一个 role** 的量级。

### 簇 6 · `out-harvest`(253) ↔ `out-mineral`(148)：47%

共享 32 条（占小文件 47%）：到目标房 → 挖 → 存容器 / 交给搬运工。
差别在挖的是 `SOURCE` 还是 `MINERAL`、以及交付对象。
可共享「到矿房 + 挖 + 交付」主干，资源类型参数化。

## 不建议合并的（避免误伤）

- **Economy 组**：`carrier`(1307) / `worker`(601) / `transporter`(210) / `universal`(263) / `manager`(256) /
  `harvester`(111) / `miner`(216)。逐字重合极低（`carrier ↔ out-carry` 仅 2%），
  **它们大而不同**，是真实业务复杂度，不是重复。别为了行数去合。
- **工作层样板**：`runWorkLayer(creep, { onSource, onTarget })` + `WORK_EVENTS.STAY/TO_TARGET/TO_SOURCE`
  被 **15 个文件**复用，样板看起来多，但再抽一层（比如把 onSource/onTarget 变成数据表）
  会把「这个角色什么时候回源、什么时候送货」这层可读性埋掉。列为低优先。

# 已实施（第 2 轮）：upgrader / worker / up-upgrade 分工收尾

`7e72aea`（worker 吸收 upgrader）只做了前一半——「upgrader 转型冲级专员」停留在提交信息里，
代码里 upgrader 成了死配置（executor 指向 worker、`RoleSpawnCheck` 无条目 → 永不孵化），
冲级只能靠旗帜手动开。本轮补齐：

## 编制阶梯（唯一入口 `shared/roomWorkforce.getUpgraderTarget`）

| 模式 | 定编 |
|---|---|
| low / main / stop | 0（升级由 worker 兼任） |
| high / mini | `min(RCL 人口上限, ceil(升级 work ÷ 每只 WORK 部件), 控制器工位数)` |
| rush | 同上，但工位数取 `max(冲级工位, 控制器工位)`；RCL8 直接 0 |

- **RCL 人口上限**（`UPGRADER_POP_CAP_BY_LEVEL`，1→3 / 2→4 / 3→6 / 4→6 / 5→7 / 6→8 / 7→8 / 8→6）：
  升级预算按 **WORK 总数** 给（30/90 work），人口要除上每只的 WORK 部件数才能折算；
  低 RCL 能量容量撑不起大体型时 `GetRoleBodys` 会退到 1 WORK 的体型，
  同一笔预算就折成几十只——线上 RCL3 冲级房实测 **38 只升级工**，
  既吃穿房间能量（`energyAvailable` 长期低于 spawn 闸门 → 采集/搬运都孵不出来 → 房间停摆），
  又用几十次孵化独占 spawn 队列。与 `WORKER_POP_CAP_BY_LEVEL` 是同一类问题的同一套解法。
- 取值权衡：`high`/`mini` 的缺口会转由 worker 承接升级，上限不影响总吞吐；
  但 `rush` 里 worker 不兜底，**上限即吞吐上限**，所以不能压到最小（3~4 只会让冲级明显变慢），
  取 5~6 折中。高 RCL 体型大（例如 15 WORK，90÷15=6）折算结果本就落在上限内，不误伤正常编制。
- 折算与 worker 升级侧同源（都用 `getUpgradeWorkTarget`），只换角色承接，两档口径不漂移。
- `getWorkerUpgradeTarget` 扣除 upgrader 已承担的升级 work——「减轻 worker 负担」的落地；
  `hasWorkerUpgradeDemand` 随之改用扣减后的口径。

## 冲级工位（自动判定，不靠开关）

`getRushUpgradeSlotList`：**同时**满足「与控制器旁 storage/terminal 相邻」和「位于控制器 3 格内」
的可站格。数量即布局对冲级的支持程度——一格都没有就回退成普通升级工并缩编。
**不要简化成「有没有 storage/terminal」**：仓库在但旁边站不下人，同样不支持。

## 行为（`action/economy/upgrader.ts`）

- rush + 布局支持 → **直接委托** `support/up-upgrade`（零复制）；否则走普通升级
  （从 7e72aea 删除的旧 upgrader.ts 恢复，取能 `acquireEnergy` + `runControllerUpgrade`）。
- `up-upgrade` 角色、执行器、`UP-UPGRADE` / `AID-UUP` 旗帜入口**原样保留**：
  既是手动开冲级的开关，也是这条新路径出问题时的参照与回退手段。

## 工位名册拆分

- 建造配额名册 `WORKER_FAMILY_ROLES = ['worker']`——upgrader 不占建造配额；
- 升级工位名册 `UPGRADE_SLOT_ROLES = ['worker', 'upgrader']`——两族共用一张，避免抢同一格；
- rush 且布局支持时，升级工位池整体切到冲级工位（取能点就在旁边）。
