# 核心架构设计（Design Patterns 视角）

## 1. 架构目标与约束

RosmarinBot 的核心不是“文件怎么组织”，而是“在 Screeps 的 tick 模型下，如何让复杂自动化稳定演进”。

项目在以下约束中做设计：
- **单线程、强时序**：每 tick 必须完成决策并输出动作。
- **状态长期驻留**：Memory 是长期状态，global 是短期运行态。
- **CPU 预算波动**：bucket 起伏会直接影响行为可持续性。
- **业务域很多**：孵化、运输、外矿、生产、防御、跨 shard 同时存在，且会互相抢资源。

核心目标：
- 保持主循环稳定（可降级、可恢复、可观察）。
- 让新功能“接入成本低、耦合成本低”。
- 保证策略可替换，而不是硬编码在单个业务流程里。

---

## 2. 整体设计模式地图

| 设计模式 | 解决的问题 | 在项目中的体现 |
|---|---|---|
| 组合根（Composition Root） | 把系统装配集中到一个入口，避免隐式依赖 | `main.ts` 统一挂载 prototype、console、runtime module、infra side-effect |
| 生命周期钩子（Lifecycle Hooks） | 在统一时间轴上组织全局逻辑 | `init/start/tick/end` 四阶段调度 |
| 运行器模式（Runner Pattern） | 把“遍历对象”与“对象行为”解耦 | room/creep/powerCreep/flag runner |
| Actor + Mixin | 用领域对象承载行为，按能力模块组合 | `Room/Creep/Flag/PowerCreep` 通过 prototype 插件组合方法 |
| 命令队列（Command Queue） | 将“决策”和“执行”拆分，降低抢占冲突 | MissionPool 的 add/get/lock/submit 流程 |
| Repository / Gateway | 屏蔽 Memory 细节，统一访问边界 | `modules/utils/memory.ts` 的 `getX/ensureX` |
| 策略模式（Policy/Strategy） | 在资源波动时切换执行策略 | QoS 的 `updateQoS/shouldRun/isTickAligned` |
| 时间解耦（Temporal Decoupling） | 让任务不必在当前 tick 立刻执行 | `global.event` 延时事件系统 |
| 保护壳（Error Boundary） | 局部失败不拖垮主循环 | `errorMapper(exec)` 包裹主执行链 |

---

## 3. 组合根模式：系统装配只在入口发生

入口层只做三件事：
1. **挂载能力**：prototype 扩展、console 命令、infra 全局能力（如 QoS）。
2. **注册模块**：把运行时模块注册到生命周期。
3. **交付 loop**：由框架统一驱动执行。

这使系统具备两个关键特性：
- 依赖方向单一：业务模块不负责“拉起系统”。
- 装配可审计：看入口即可知道系统到底启用了哪些能力。

---

## 4. 生命周期微内核：Hook 驱动而非模块互调

`createApp` 本质是一个轻量微内核：
- 内核只定义时序与调用协议（`init/start/tick/end`）。
- 业务模块只实现自己关心的 hook。
- 模块之间通过共享状态（Memory/global）协作，而不是直接强引用互调。

收益：
- 模块替换成本低（新增/删除模块几乎不动其他模块）。
- 启动顺序可控（注册顺序即执行顺序）。
- 适合逐步演进（先挂载基础模块，再追加功能模块）。

---

## 5. Runner + Actor：遍历与行为分离

主循环不关心“每个对象做什么”，只负责“把对象交给 runner”。

runner 再调用对象行为（如 `room.exec()`、`creep.exec()`）。  
对象行为通过 prototype 插件拼装，形成“能力集合”。

这是 **调度层** 与 **领域层** 的分离：
- 调度层：统一节奏与错误边界。
- 领域层：按对象职责实现细节策略。

---

## 6. Prototype 插件化：Mixin 组合能力，而不是巨型继承链

Room/Creep/Flag/PowerCreep 的能力不是写在一个超大类里，而是按功能拆成插件再组合挂载。

这种 Mixin 方式解决了两类问题：
- **横向扩展**：新增能力时，不必改已有“核心基类”。
- **演进隔离**：防御、外矿、任务、结构控制等能力可独立迭代。

代价是命名与约定必须严格：
- 方法命名冲突需要控制。
- 插件之间共享状态字段需要统一语义。

---

## 7. MissionPool：命令队列模式的核心实现

该项目大量行为采用“先生成任务，再由执行者消费”的命令队列思想。

核心链路：
1. **生产任务**：业务模块写入 mission pool（按类型与优先级）。
2. **获取任务**：执行者按优先级/距离/条件筛选。
3. **锁定任务**：避免多执行者重复消费。
4. **提交任务**：按执行结果更新或删除任务。

这是典型的“决策与执行分离”：
- 决策层关心“应该做什么”。
- 执行层关心“能不能做、做了多少、何时结束”。

它显著提升了并发场景稳定性（尤其在运输、孵化、矿务等高冲突领域）。

---

## 8. Memory 访问层：Repository/Gateway 模式

`modules/utils/memory.ts` 不是工具函数堆，而是存储边界：
- 统一根节点（`Memory.RosmarinBot`）。
- 统一初始化与兜底逻辑（`getX`/`ensureX`）。
- 明确哪些读取允许“隐式创建”，哪些必须显式创建。

这样做的价值：
- 避免业务代码到处散写 `Memory.xxx ??= ...`。
- 把内存结构演进风险集中在一层处理。
- 为迁移/清理/版本化预留稳定入口。

---

## 9. QoS 策略模式：在不稳定 CPU 预算下保持系统存活

QoS 被设计为全局策略服务（`global.qos`），而不是让业务模块直接依赖 infra 实现细节。

关键思想：
- 每 tick 先计算环境状态（bucket/used -> level）。
- 业务逻辑通过策略 API 查询“本 tick 是否应执行”。
- 用 `every/minBucket/allowLevels/levelAtLeast` 做细粒度门控。

这是一种 **策略外置**：
- 业务模块只声明“执行条件”。
- 不关心 QoS 如何判定。

结果是：
- 降级行为统一，不会每个模块各搞一套“低 bucket 判断”。
- 易于后续调参和集中治理。

---

## 10. 延时事件系统：时间解耦而非即时耦合

`global.event` 提供轻量延时调度能力：
- 可延迟 N tick 执行。
- 可按函数条件触发。
- 可设置最大执行次数与终止条件。
- 与 `start/tick/end` 生命周期对齐。

这使得“当前拿不到条件、但未来要执行”的逻辑不用硬塞进当前流程里。  
属于典型的 **Temporal Decoupling**（时间解耦）。

当前设计刻意保持轻量：
- 仅驻留 `global`，不做 Memory 持久化。
- 保证运行中新增事件不会在同轮立即重入执行。

---

## 11. 稳定性模式：失败隔离与可观测

主循环使用错误映射保护壳：
- 业务异常不会直接打断框架层流程。
- 报错可映射回源码位置，降低排障成本。

同时通过统计与状态上报（如 QoS 写入 stats）保持可观测性，支撑运行期调优。

---

## 12. 这套架构的本质

RosmarinBot 并不是“按文件分层”的架构，它是“按控制问题分层”的架构：
- **时间控制**：生命周期 + runner + event。
- **资源控制**：QoS + mission 优先级 +策略门控。
- **状态控制**：Memory Gateway + global 运行态。
- **复杂度控制**：prototype 插件化 + 模块化 hook。

这让项目可以在持续加功能时，依然维持：
- 执行顺序清晰
- 依赖方向可控
- 局部失败可承受
- 策略调整可落地

---

## 13. 新功能接入的架构准则

新增能力时，优先遵循以下顺序：
1. 是否能作为独立 runtime module 接入 hook？
2. 是否应通过 mission pool 与执行层解耦？
3. 是否需要 QoS 门控与节流策略？
4. 是否应通过 memory gateway 读写状态？
5. 是否需要延时事件而非同步强耦合调用？

只要按这套准则扩展，系统规模增长时仍能保持可维护性。
